Why the reference scored 8.834
==============================
The user supplied an actual official result for the DS submission:
5d8297ed09d2309e0f3685dd83f0612617e36e2c, amd-cagra-submit:
8.834/20, build=1.443x, query=1.033x, gates=pass.
It is NOT a confirmed score for our parent 55d78dc candidate.
Compared with the frozen implementation, that DS version changes only the
NN-descent iteration budget (100 -> 70 for high dimension, otherwise 10).
It retains intermediate/final degree 256/128 and the default SINGLE_CTA search
with candidate budget 512 and search width 4.

Under the published formula, if all gates pass:
  score = 4 + 14*clamp(ln(build)/ln(3),0,1)
            + 2*clamp(ln(query)/ln(1.5),0,1).
Dataset ratios use a weighted geometric mean: SIFT 0.4, Hidden256 0.6.
The rounded supplied ratios yield 4 + 4.67330 + 0.16015 = 8.83344.
Rounding explains the reported 8.834. With build fixed at 1.443x, even maximum
query credit would only reach 10.6733. Both construction and search need work.
Full speed credit requires weighted build >=3x and query >=1.5x, plus all gates.

Implementation
==============
Uniform, dimension-independent policy:
  NN_DESCENT; intermediate_graph_degree=96; graph_degree=96; niter=5.
  itopk_size >= max(4096,4*topk); search_width=1; search algo=AUTO.
The fixed C API defaults to SINGLE_CTA, not AUTO. Explicit AUTO dispatches the
tested individual queries to multi-CTA search. Its higher throughput permits a
larger candidate pool, recovering recall lost by making graph construction
cheaper. These are ordinary fixed-library parameters; the library is unmodified.
No custom search, data-dependent selection, phase detection, graph caching,
cross-build reuse, new runtime dependency, or altered FP32 interface is used.
SQL behavior, persistence, CPU VSAG path, and build entry point are unchanged.
