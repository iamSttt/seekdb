Evaluation requirements still applying
=====================================
Only the official platform can establish the score and all gates. It checks
both formal datasets, Recall absolute thresholds and <=0.005 baseline decline,
per-dataset geometric-mean query ratio >=0.90, unique and valid IDs, actual GPU
construction/search, CPU-path functionality, stability, and resource limits.
Physical VRAM must be <=45 GB and <=1.25x the same-round baseline. Development
VRAM sampling is not an exact peak or a substitute for that gate.

The same newly source-built seekdb kernel was used for both runs. Relative to
the frozen baseline, the parent modifies only the bridge; the kernel source is
unchanged. Each run started a separate, empty instance; LD_LIBRARY_PATH selected
the corresponding bridge and /proc/<pid>/maps verified the loaded library.
Candidate ran first, then baseline; no server or graph was shared between runs.
Both used a 24-CPU affinity mask, a 16 GB seekdb memory budget, and the exact
index/search SQL parameters in the task. Import and startup were outside timing.

Measured end-to-end build speedup is approximately 1.234x and geometric-mean
query speedup approximately 1.005x on this synthetic dataset. Both completed all
queries with complete, unique, valid IDs. Neither recall metric regressed.
Device VRAM was sampled every 50 ms, including import/build/query; the ratio is
approximately 1.0005x, but sampling cannot establish an exact peak-memory gate.
These are local measurements from one pair, not an official competition score.

The initial large import hit the default query timeout. The development harness
now sets session query/transaction timeouts before import; the paired runs above
completed after that correction. No candidate implementation change was needed.

Rejected approaches
===================
Persistent query-buffer caching showed no meaningful gain in 4,096-query runs.
Team/block-size overrides slowed searches. Default IVF-PQ construction lost
substantial recall; an enhanced IVF-PQ build was stopped after more than nine
minutes without completion. None of those implementations is included here.

GPU profiling evidence and limitation
====================================
rocprofv3 successfully recorded 688 GPU dispatches from the exact compiled
candidate bridge on synthetic250K x 256, including 100 NN-descent local-join
dispatches, CAGRA graph pruning, and 35 CAGRA search dispatches. Kernel summaries
are included in results/candidate_profile_summary.json. These profiled timings
are not used for the performance ratios above.

Launching the full seekdb process under rocprofv3 preload aborted during the
unchanged ObTimer initialization, before SQL service startup. Repeating that
control with the frozen bridge produced the same initialization abort. Ordinary
SQL startup/build/query succeeded for both libraries. Consequently, local
end-to-end SQL profiling is UNVERIFIED; the bridge trace does not establish the
organizer's full gpu_path gate. No product code was changed to bypass profiling.
