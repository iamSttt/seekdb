Implementation and reason
=========================
The existing single-query adaptor created and joined a 32MB-stack pthread on
every GPU search. That large stack is necessary for the fixed cuVS library, but
repeated OS-thread and GPU thread-local initialization is not.

CuvsSearchWorker retains one 32MB-stack pthread for synchronous single-query
jobs. The original registry mutex still protects index lifetime/freshness.
Submission holds its buffers alive until the worker signals completion; a
separate submission mutex prevents pending-job replacement. The worker stops
and joins on destruction. If initial thread creation fails, the original
per-query large-stack thread path is used. CPU VSAG, filtering/fallback, result
allocation, index persistence and the explicit batch path are unchanged.

The bridge is byte-identical to v2: NN_DESCENT, intermediate/final degree96,
niter5, AUTO search, itopk>=max(4096,4*topk), width1. Fixed hipVS is unmodified.
No query-result cache, graph reuse across builds, phase detection, or hidden-data
selection has been introduced. GPU work still runs through the fixed CAGRA API.

Functional and concurrency validation
=====================================
test_worker.py extracts the actual class from the adaptor and compiles it with
ASan and UBSan. It passed 16000 calls from concurrent submitters over ten worker
lifetimes; verifies callback results, same worker identity, different caller
identity, actual >=32MB stack, clean shutdown/join, and failed startup behavior.

The new kernel was restarted on its SIFT SQL instance, verifying persisted index
load. Eight clients issued 256 total independent top100 queries concurrently;
recall100=1.0 with valid unique IDs. The same live process then created, queried,
filtered and dropped newly named 512x16 test tables through cuvs,cuvs,vsag,cuvs
backends. Every cycle had recall10=1.0 and filtered-ID integrity passed. Existing
benchmark databases were preserved. This checks repeated index lifetime changes
with the shared worker and the unaffected CPU fallback path.

No claim of race-freedom from sanitizers: ASan/UBSan are not ThreadSanitizer.
The mutex/condition handoff is reviewed and stressed, while formal stability
and hidden-data gates still require platform evaluation.
