# 受限的大批量向量输出候选

本轮落实用户“保证现有优点的基础上优化退化的点”的要求。方向属于 user；本候选、启用条件、实验和后续取舍均由 assistant 完成，不新增或代写用户预测。

上一轮等值专用路径与DOM行容量预留共138对已完成，均缺少足够的净收益依据。当前运行源码撤去这两个候选；完整实验实现仍在 `76d7687b6eb002bb765bb555102d528166af50ac` 与其归档产物。详见 [上一轮记录](REGRESSION_FOLLOWUP_20261113.md)。

新候选 `MVDB_TYPED_BULK_VECTOR_ONLY` 默认关闭，在原四宏基础上单独试验。原来投影包含至少128维向量就用typed writer的规则保持；新增规则要求实际投影至少16维向量、没有WHERE、LIMIT至少4096或不限行，并且当前 `pk_pos.size()` 至少4096。活跃PK计数是O(1)，不扫描墓碑；距离表达式本身不算向量投影。这样只为确定会返回大量行的16–127维投影复用已有直接编码器，小结果集、标量输出与过滤查询沿用原规则。

这仍是待测的保守范围，并非最优阈值证明。JSON直接编码的错误处理、精度、UTF-8和外排payload所有权都不改。诊断计数只在单测宏下编译，用于证明实际调用的编码器；测量程序无这些计数开销。

新单测覆盖15/16/64/127/128维、4095/4096行与LIMIT、WHERE、标量/距离投影、排序、删除墓碑、回滚重插、原128维小结果规则，以及12项bulk UTF-8失败清空输出与后续恢复。它配合原有实际程序的协议、TopK和54项UTF-8门禁，不将静态检查写成Linux测试结果。

## 预先固定的测量

基线为交付 `e020fdeb67dd8b64b77f0f8c2905f137f0112bba` 的四宏原PGO，候选仅追加bulk宏，使用各自源码独立构建与原训练。比较84对：候选66对，另18对同一个基线程序的A/A控制。

- standard10k、resident30k、filter60k各15对，每阶段1000请求，保留首条、前64、后936、奇偶子组及完整已计时生命周期。
- many16、many64、many127、spill低/高命中、wide128、wide768各3对；三个低/中维场景均8192行，测试器的旧默认用例不变。
- A/A为resident30k、filter60k、many16各三种子两对，AB/BA各一。对照主机/进程波动，不等于独立PGO构建控制。

所有原始负对、启动/导入停顿保留。复核响应完整值、精确身份、输入、源码、profile、实际flags及二进制SHA；计时总和与端到端wall区分。大输出候选需要在多个维度获得可重复的查询收益，同时检查原有spill/宽输出及普通查询的损失。若不满足就不采用；3对筛查不能推广为所有数据规模或正式成绩。
