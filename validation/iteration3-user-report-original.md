我共提出 **20 项改进方案**，其中 13 项针对运行实现。最先进入技术验证的候选是：**I03 驻留预算、I04 UPDATE 落盘、I05 复合过滤、I08 批量磁盘写入**。如果正式负载主要是小规模静态查询，我会把 I13 解析分配、I15 PGO/LTO 和材料线前移。

### 2.2 我采用的评分口径

本次浏览无法直接读取用户提供的语雀赛题全文。我以下采用**指定提交内保存的题面核验记录与计分工具**，不声称已经实时确认当前题面全部条款。正式规则或平台实现若有更新，应以组织方当前说明为准。[S2][S3]

按归档规则，性能由写入、查询两阶段组成，权重为 **1∶2**；每阶段时间 T、I/O 字节 B、内存 M 的权重为 **0.6／0.2／0.2**。工具采用：

```text
R = (三轮基线对应指标的中位数 + ε) / (候选本轮对应指标 + ε)
f(R) = R / (1 + R)
E阶段 = 0.6 × f(RT) + 0.2 × f(RB) + 0.2 × f(RM)
E本轮 = (E写入 + 2 × E查询) / 3
E = 三轮候选 E本轮的中位数
εT = 0.001 秒；εB = εM = 1 MiB
```

这个公式有界，与历史平台显示的数千分 E 尚无已验证的尺度对应。因此，我不会把本地加速比直接乘到平台 E，也不会用它计算排名点数。查询时间、构建代价、I/O 与内存必须一起评估。[S3]

材料侧的归档规则强调五类学习证据：问题理解与自主拆解、技术理解与迁移、独立验证与质疑、实验与反馈迭代、取舍与反思。Agent 的实现和解释不能自动变成我的独立技术贡献；同一条纠错链也不能换几个维度重复计算。历史平台的“无效／待复核／范围／摘要”组合提示，没有确定是哪一项失败。[S2]

## 五、性能与诊断方案的具体实施判断

### I01：我先取得正式分项与 Prompt 失败细项

**我的依据：**当前缺少 `ee299ad` 的正式 T/B/M、有效 Prompt 原始分和评审失败分支。历史相同运行实现出现不同 E，也表明我不能靠跨次显示分数解释性能变化。[S2][S6]

**我的做法：**核对平台实际锁定的提交、镜像、材料路径、字节数、SHA-256、规则版本，以及可提供的三次独立评审状态、维度结果、失败引用或结构校验项；性能侧同时取得写入／查询分项和输入规模。必要时由我方依据这些具体字段向组织方咨询。

**我的预估：**若能获得细项，定位主要诊断分支的可能性为 **50%—75%**；若仍只有现有组合提示，则我将其下调至 **20% 以下**。成功标准是能够区分输入提取、内容证据、评审输出及平台校验问题，不能仅以提示消失作为解释。

### I02：我把单一小负载扩展为能命中边界的性能矩阵

**我的依据：**归档标准 benchmark 主要是 10,000 行、128 维、K=10、Gaussian 数据和固定过滤结构。它难以揭示 resident 切换、较大 K、更新后落盘及复合过滤的成本。[S6][S15]

**我的做法：**先做小型筛选矩阵：行数 10k／30k／35k／50k／100k，维度 16／128／768，K=1／10／100，过滤命中率 0.1%／1%／10%／100%；按实际支持范围选取代表组合，加入多列过滤、离群值及修改后查询。对胜出方案再扩大覆盖。我也会补录构建、重启、临时文件和最终写回的资源边界，不用 RSS 或缺失值替代正式 M/B。

**我的预估：**发现至少一个可复现、可据此选择实现的瓶颈，可能性为 **75%—90%**。这个目标是提高后续优化命中率，本身不保证正式 E 上升。

### I03：我修正 resident 索引仍沿用旧布局的预算判断

**我的依据：**`flat_index.cpp:64–67` 用 `4×dimension+16` 判断每行驻留成本，但当前 resident 实际借用向量，主要保存指针、PK、slot，另加辅助结构。128 维、16 MiB 预算时，旧判断约在 **31,775 行**之后就转磁盘；这不等同于真实元数据已用尽。[S8]

**我的做法：**按实际容器容量、posting、量化码、分区及构建峰值重新核算预算，同时计入原表已经拥有的 payload。先做预算修正，随后才决定是否改变全局限额，避免一次实验混入两个因素。

**我的预估：**在切换边界附近、且原表仍驻留的负载上，达到性能目标的可能性为 **65%—85%**。我会重点测 30k／35k／50k、多表竞争与分配失败；若实际内存峰值超出预算，局部提速也不保留。

### I04：我避免少量 UPDATE 让整张小表进入磁盘路径

**我的依据：**修改语句会经过语句事务包装；`update_rows()` 在事务活动且表尚未落盘时调用 `spill_payloads(tb,true)`。因此，一条命中少量行的 UPDATE 也可能触发整表 payload 落盘，并在当前打开周期内失去 resident 查询路径；这不意味着重启恢复后仍必然落盘。[S9][S10]

**我的做法：**为少量旧值保留有界内存 Undo；超过阈值后，再选择 Undo 溢写或表迁移。它与 I03 不同：I03 改索引准入，这里改 UPDATE 对原表存储状态的影响。

**我的预估：**在“少量更新、随后大量查询”的负载上，成功可能性为 **60%—80%**；纯静态查询几乎没有此项收益。我会比较更新 1／10／100 行后的查询总成本，覆盖失败语句回退、显式事务回滚、跨表 spill 与 SIGKILL 恢复。

### I05：我让复合过滤选择真正更小的候选集合

**我的依据：**现有 posting 主要缓存一个 BIGINT 列；交替过滤不同列可能重建，复合条件通常使用遇到的第一个等值项，而未必是选择性最高的一项。单 BIGINT 等值已经有快速路径，不能重复算新增优化。[S8][S9]

**我的做法：**实现有界多列 posting 缓存，按候选数量选择访问路径；在收益明确时支持范围查找和 posting 交集，所有剩余条件继续按原 SQL 语义验证。

**我的预估：**复合过滤、偏斜数据或列间交替场景，成功可能性为 **55%—75%**。我会测零命中、低选择率和接近全表命中，防止维护成本使简单查询退步。

### I06：我用小型增量区减少修改后的全索引重建

**我的依据：**插入、修改、删除会使物理索引失效，下次查询可能重新执行全表索引构建、排序、量化及 posting 准备。[S9]

**我的做法：**保持稳定索引主体，为新增或修改行设置小型 delta，为删除设置 tombstone；查询精确合并主体与增量的 TopK，达到明确阈值后再重建。借用指针必须有稳定生命周期，不能继续引用已扩容或替换的行存储。

**我的预估：**在写入与查询交替的负载上，成功可能性为 **50%—70%**。这是较高投入方案；我会先证明重建确为热点，再验证重复主键、删除、回滚、重启及 delta 合并。先导入再静态查询时，我不会优先做它。

### I07：我把 spill 表的过滤字段与完整行读取分开

**我的依据：**spill 路径读取行时需要读取并反序列化完整记录；向量索引已有向量副本，但复合过滤仍可能为了少量标量字段再次取整行。[S9]

**我的做法：**为经常使用的过滤字段维护紧凑、有界的列式元数据，先过滤，再访问必要向量，最终只为选中的 K 行取完整投影。该方案处理落盘数据，与 I05 的 resident posting 改进可以分开验证。

**我的预估：**在大表、高选择性过滤场景，成功可能性为 **55%—75%**。我会同时检查多份元数据的一致性、额外内存和总 I/O；如果只是把整行读取换成昂贵的随机访问，便不满足目标。

### I08：我把磁盘索引构建和 payload spill 的逐行写入合并

**我的依据：**磁盘 FlatIndex 构建仍逐行组织记录并执行 `pwrite`，扫描端已经按约 1 MiB 块读取。payload spill 也存在逐行写入路径。这是构建端的新空间，不是重复增加已有 WAL 缓冲。[S8][S9]

**我的做法：**用 256 KiB—1 MiB 的有界缓冲聚合构建写入，复用记录空间，并保持偏移、短写、EINTR 和失败清理语义。

**我的预估：**在构建或落盘占比较高的场景，成功可能性为 **65%—80%**。我会测“构建＋后续查询”的总成本、系统调用次数、B/M 和重建频率；建索引单项变快不能直接等同正式查询阶段涨分。

### I09：我改进现有并行决策，而不是强制开启双线程

**我的依据：**当前已有启动唤醒校准，但扫描成本预测仍使用固定的约 10 ns／行；实际成本还受维度、K、量化拒绝率和过滤候选数影响。[S11]

**我的做法：**用少量真实工作量校准每维、每候选成本，在 cgroup CPU 限额下决定是否分片；足够大的过滤候选集合也可参与判断，同时设置校准开销上限。

**我的预估：**大规模、高维负载上成功可能性为 **40%—60%**。我会比较 1／2 CPU、不同维度与 K 的完整请求延迟及 CPU 消耗。历史无条件双线程只有微小墙钟收益、明显 CPU 增量，不能据此直接强开。[S6]

### I10：我让安全下界按块累计，争取提前拒绝远点

**我的依据：**当前候选可能依次计算完整 int8 界、完整 float 界，再对幸存者计算 canonical exact 距离。远点即便最终被拒绝，也可能已读取全部维度。[S10]

**我的做法：**每 16／32／64 维累计一次可证明安全的下界，一旦严格超过当前阈值就结束；保持最终精确距离、平局 PK 顺序和数值边界语义。

**我的预估：**成功可能性为 **35%—55%**。我会使用独立数值 oracle，覆盖极值、次正规数及舍入边界；若 Gaussian 高维距离过于集中，或分支成本超过节省，我会回退。

### I11：我改善全表单一量化尺度对离群值的敏感性

**我的依据：**当前量化主要使用全表 `max_abs` 决定公共 step；个别极值可能使其他点的界变松。量化码还有 4 MiB 上限，较大数据可能失去这一筛选层。[S8]

**我的做法：**试验分块尺度或逐行保守误差半径，按实际拒绝收益分配量化预算，保留精确复核。新的尺度必须有正确的误差包络，不能把近似 int8 距离直接作为 exact 排序键。

**我的预估：**在离群值或量化受限负载上，成功可能性为 **35%—55%**。我会同时计入码本、误差元数据、构建与查询成本，比较 Gaussian、聚簇和含极值数据。

### I12：我先用少量代表候选收紧 TopK 阈值

**我的依据：**现有 norm 排序与具体 query 无关，遍历前段不一定包含较近的候选；初始阈值过松会降低后续安全筛选效率。[S9]

**我的做法：**先访问少量有代表性的点或块，建立初始 K 阈值，然后仍完整覆盖其他候选。先导点不能重复计入结果，所有精确语义保持一致。

**我的预估：**成功可能性为 **35%—55%**。我会比较 0／32／64／128 个先导候选，检查选择成本、访问局部性、K 边界和 PK 同距；小数据下我预期它可能没有净收益。

### I13：我减少 SQL token 与语句对象的重复分配

**我的依据：**`sql.cpp` 的 token 仍拥有 `std::string`，解析存在复制和容器分配。当前已经使用快速数值解析、简单字符串路径和并行 literal materialization，这些不是新增方案。[S12]

**我的做法：**对无需解码的 token 使用生命周期安全的 `string_view`，只为转义结果拥有内存；用有界语句 arena 复用容量。只有在 profile 证明必要时才增加语法模板缓存，并确保每次重新绑定查询向量、字面值和 schema。

**我的预估：**解析占比较高的小查询或导入场景，成功可能性为 **40%—60%**。我会验证转义、UTF-8、错误定位、多语句拒绝和异常后的复用，防止缓存接受错误输入。

### I14：我减少逐行结果编码的小型 JSON DOM

**我的依据：**当前已直接输出响应外壳，但 `encode_json_row()` 仍为每行创建 `Json::array()`、逐 cell 填充再 `dump()`。[S10]

**我的做法：**为 BIGINT、有限 double、字符串和向量提供类型化行编码，复用经过验证的转义及浮点输出规则，减少临时对象。

**我的预估：**大结果集或宽投影场景，成功可能性为 **35%—55%**；K=10 的常规查询可能收益很小。我会检查 INT64 精度、负零、double 往返、非法 UTF-8，以及编码中途失败后整条响应清空。

### I15：我在固定编译器的 O3 基础上比较 LTO 与 PGO

**我的依据：**根 Dockerfile 已使用固定 GCC 13.3、`-O3` 和静态链接，但没有 LTO 或 profile feedback。因此，升级到 O3 已经没有增量，LTO/PGO 才是可验证的编译路线。[S13]

**我的做法：**用同一源码比较 O3、O3＋LTO、O3＋PGO、O3＋PGO＋LTO；训练数据覆盖读写、维度、过滤和错误路径，并与验收数据分离。GCC 官方文档说明了 LTO 及 profile-generate/profile-use 机制。[S16][S17]

**我的预估：**成功可能性为 **45%—65%**。我会检查端到端收益、二进制大小、构建成本和不同 CPU 路径；保持现有数值语义及 CPU 派发，避免训练集偏置造成局部提升、整体退步。

## 六、材料与评审有效性的增量方案

### I16：我通过语义压缩释放材料空间

**我的依据：**当前 JSON 已经是紧凑单行，继续删空白无效。21 个实验约占材料的 43.4%，证据解释约占 22.3%；其中存在重复的 Agent 背景与局限说明。[S4]

**我的做法：**保留真实原话、作者归属、关键结果、必要来源及限制，合并重复事件说明，压缩弱证据的元描述，为新证据释放 **12—20 KiB**。核心证据仍内置 JSON，不能全部移到评审不一定读取的外链。

**我的预估：**在不丢失上述信息且校验通过的前提下，释放目标容量的可能性为 **80%—95%**。我会检查全部 pointer／quote、有限数值、重复键、字节数和两副本一致性；精简成功不等于官方分数已提高。

### I17：我亲自形成一条完整、独立的实验闭环

**我的依据：**当前材料已诚实说明，用户侧多为目标、授权和结果反馈；技术解释、实现与实验大多由 Agent 完成。继续增加 Agent 撰写的说明，不能自动填补这个缺口。[S4]

**我的做法：**我从 I03 或 I04 选择一个实际问题，先用自己的话说明假设、原因、预期和反例，再审阅配对结果，解释预测与结果的差异，最后作出保留或回退判断。Agent 可以协助执行，个人贡献必须按实际作者保留。

**我的预估：**在本人真实参与并保留完整记录的前提下，形成一条来源完整、可供评审的学习证据，可能性为 **70%—90%**。我不会提前设定它应得几分，也不会把本报告中的计划追写成历史发言。

### I18：我用第二场景验证知识迁移

**我的依据：**单一负载上的结论不足以体现适用边界。归档规则也不支持把同一纠错链拆成多个维度重复计分。[S2][S4]

**我的做法：**在一个真实实验完成后，我会事先解释把结论用于第二场景的理由，例如从 resident 到 spill、从单列到复合过滤，或从 128 维到 768 维；再用实际结果说明哪些规律成立、哪些失效。

**我的预估：**形成一条有区分、可核验的迁移证据，可能性为 **60%—80%**。验收要求第二场景确实运行、预测记录早于结果、本人判断可定位；仅换一个随机种子，我不将其包装成新的知识迁移。

### I19：我寻找已经存在的历史原始技术发言

**我的依据：**一些历史 ADR、技术陈述和选项选择来自旧提交材料或二手转录；当前归属声明不能补齐原始 message ID、完整上下文与发生顺序。[S4][S5]

**我的做法：**查找已有聊天导出或原始记录，对能找到的技术发言补充真实 turn/message ID 和上下文；找不到的继续保留来源限制。我的目标是恢复已经存在的证据，不是重建理想化历史。

**我的预估：**找到至少一条足以改善来源定位的技术记录，可能性为 **20%—45%**，取决于原始资料是否仍在。我会给这项调查设时限，避免它阻塞新的真实实验。

### I20：我统一材料文档、生成器与当前验证入口

**我的依据：**当前材料采用五维组织，但旧 `CONVERSATION-GUIDE.md` 和生成器仍包含四维框架及 `score_hint`，旧 CI 还有重新生成材料的检查；README 已提醒旧工具不能覆盖当前材料。这是潜在误用风险，不能据此声称当前验证已经失败。[S14][S19][S20][S21]

**我的做法：**更新文档和工具入口，使其与当前归档规则一致；阻止旧 raw 生成器覆盖当前证据，移除容易误解为官方自评分的建议，同时保留来源和哈希校验。

**我的预估：**消除两套材料契约与误覆盖风险的可能性为 **90%—98%**。它属于保分基础设施；我的验收是合法材料稳定通过，坏引用、角色错配和附件哈希错配仍被拒绝，构建流程不再误覆盖。历史作者真实性继续保留独立核查限制；这些机械检查不能承诺官方评分增加。

## 七、我暂不优先投入的路线

| 路线 | 我的判断 |
| --- | --- |
| 再次同步材料副本、修哈希、删除自定 tier | 指定提交已经完成这些工作。我会保留校验，不把它们重复列为新增提分 |
| 默认开启 ahead8 软件预取 | 既往 code／row／both 三组合整体配对中位均未胜过关闭状态。我只有在新 profile 指向不同瓶颈时才重试 |
| 无条件开启双线程 | 历史同源实验墙钟中位收益约 1.0094×，CPU 增加约 23%—27%；当前已有校准机制，应先改决策模型 |
| 直接调低 ANN 扫描比例 | 当前默认 ANN 走精确路径；代码注释记录过 Gaussian 场景的召回与 gather 代价问题。我会先确认正式召回契约，再单独评估真正近似检索，不把它当作高概率捷径 |
| 直接抬高全部内存预算 | 可能减少落盘，也可能推高 M、构建峰值和多表竞争。我会先修真实记账，再按完整成本取舍 |

## 八、我的执行顺序与验收方式

### 第一批：我先解决信息缺口，并验证两个明确的路径切换问题

我会并行推进 **I01、I02、I16、I20**，形成当前提交的成绩与材料基线、边界负载和可用证据空间。技术实验先做 **I03**；正式负载包含修改后查询时，加做 **I04**。**I08** 作为较低耦合的构建路径候选并行筛选。每次实验都保留本人真实预测与判断，以落实 **I17**。

我的第一批交付标准是：拿到可解释的分项，或明确记录仍缺哪些字段；至少完成 resident 切换边界和 UPDATE 后查询的可复现对照；材料压缩后引用与来源校验继续通过。没有实际收益的候选照实回退。

### 第二批：我按负载分布决定结构改造顺序

| 正式或代表负载特征 | 我优先投入的方案 |
| --- | --- |
| 小规模、静态、K=10，解析占比明显 | I13、I15；材料侧 I17、I18 |
| 超过现有 resident 边界 | I03、I08，必要时 I07 |
| UPDATE／INSERT 与查询交替 | I04、I06 |
| 复合过滤或过滤列频繁切换 | I05；落盘后再评估 I07 |
| 高维、距离计算占比高 | I09、I10、I11、I12 |
| 大结果集、宽投影 | I14 |

我会先通过单因素对照识别收益来源，再组合候选。I03 与 I04、I05 与 I07、I10 与 I11 都可能相互影响，组合版本需要重新测量，不能连乘各自的最好加速比。

### 第三批：我用完整成本决定是否保留

我对每个候选保留同一份验收记录：固定提交与镜像、负载参数、配对延迟、写入及构建成本、可取得的 B/M、正确性检查、慢样本与回退理由。资源边界缺失时记为未知；接近噪声的收益继续验证。

我会保留现有协议、公开功能、事务、恢复、独立 TopK oracle 与相关数值边界检查，并按改动补充专项验证。公开测试通过只证明相应公开检查通过，不能替代隐藏正式准入或官方材料评审。正式提分必须由最终提交的有效结果与排名确认。[S2][S15][S18]

## 九、我的投入建议

如果只能选三个技术方向，我会先选 **I03 驻留预算、I04 少量 UPDATE 落盘、I05 复合过滤**，因为它们都有清晰的源码触发条件，且可能改变整条查询路径。若正式负载没有更新和复杂过滤，我会立即调整为 **I03、I13、I15**。

材料侧，我会把 **I16 释放容量、I17 真实实验闭环、I01 正式失败细项** 一起推进。当前更缺的是可定位的个人推理、实验反馈和官方诊断；这些工作比继续堆叠 Agent 实验描述更有明确增量。

在拿到当前提交的正式分项之前，我不会承诺任一方案能够把 E 提升到某个数值或获得某个排名点数。我的决策依据是：先选最容易被证实或推翻的候选，再用完整成本和真实证据决定投入。
